# GitProfile Manager — Technical and functional specification v2

Oct 17, 2026 · @Sergio

## 1. Overview

GitProfile Manager is a Windows desktop app that manages several Git identities (name, email, SSH key, HTTPS account and signing key) and makes Git apply the right one in each repository with no manual steps.

**Problem it solves.** Commits with the wrong email, pushes rejected for using the wrong account, and credential pop-ups when working with several accounts on the same provider.

**Platform.** Windows 10 22H2 and Windows 11. Requires Git for Windows ≥ 2.36 and Git Credential Manager (included in Git for Windows).

**Design principles**

- **Declarative, not imperative.** The app doesn't modify each repo when it's cloned: it generates standard configuration (`includeIf`, `~/.ssh/config`) that Git resolves on every operation. Existing repos are covered without touching them.
- **Explicit default profile, no global identity.** A profile marked as "default" covers every repo without a rule, and rules override it where they match. The app never changes the global `user.*` from the UI.
- **No secrets of its own.** Tokens are kept by Git Credential Manager and keys live in `~/.ssh`. The app persists no secrets and doesn't need DPAPI.
- **Git works without the app.** Everything generated is Git and OpenSSH configuration, readable and editable by hand. Closing or uninstalling the app breaks nothing.
- **Minimal writing to user files.** The app writes to its own files and only adds one include line to `~/.gitconfig` and another to `~/.ssh/config`.

## 2. How the identity is resolved

The app takes no part in Git operations: it writes configuration and Git evaluates it on every `commit`, `fetch` or `push`.

The user's `.gitconfig` includes a single rules file; the rule that matches the folder or the remote loads the profile file, which sets the identity, SSH key, HTTPS account and signing.

## 3. Profile data model

The source of truth is `%APPDATA%\GitProfileManager\profiles.json`, which only holds metadata and never secrets. The Git and SSH configuration files are derived from it and regenerated on save.

| Field | Type | Materialized in | Notes |
| --- | --- | --- | --- |
| `Id` | GUID | `profiles.json` | Stable across renames |
| `DisplayName` | text | `profiles.json` | e.g. "Work - Company A" |
| `Slug` | text `[a-z0-9-]` | File names and SSH aliases | e.g. `work` |
| `Provider` | GitHub · GitLab · Bitbucket · Other | `profiles.json` | Sets the default host and the connection test |
| `Host` | text | Rules, SSH, credentials | `github.com` or a self-hosted host |
| `GitUserName` | text | `user.name` | Required |
| `GitUserEmail` | text | `user.email` | Required |
| `SshKeyPath` | path | `core.sshCommand`, SSH alias | Optional; path with `~/` and `/` slashes |
| `HttpsUsername` | text | `credential.https://<host>.username` | Optional; the token is kept by GCM |
| `Signing` | None · SSH · GPG + key | `gpg.format`, `user.signingkey`, `commit.gpgsign` | See section 7 |
| `Rules` | list of rules | `rules.gitconfig` | See section 4 |
| `IsDefault` | boolean | `rules.gitconfig` (unconditional include) | Exactly one profile; see section 4 |
| `PreferredCloneMethod` | SSH · HTTPS | `profiles.json` | Only as the default in Smart Clone |

There is no `PersonalAccessToken` field: the token is handed to Git Credential Manager when it's added (section 6) and the app doesn't keep it.

## 4. Assignment rules

Each profile is applied through rules that the app translates into `includeIf`. There are two types and they can be combined.

| Type | Git condition | Example | When to use it |
| --- | --- | --- | --- |
| Folder | `gitdir/i:<path>/` | `gitdir/i:C:/dev/company-a/` | Everything that lives under a work folder |
| Organization / remote | `hasconfig:remote.*.url:<pattern>` | `git@github.com:company-a/**` | Repos from an organization, wherever they are |

Generated file `~/.gitprofiles/rules.gitconfig`:

```ini
# Generated by GitProfile Manager. Do not edit by hand.
# Default profile: applies to every repo without a rule.
[include]
    path = personal.gitconfig

# Rules: evaluated afterwards, they override the default profile.
[includeIf "gitdir/i:C:/dev/company-a/"]
    path = work.gitconfig
[includeIf "hasconfig:remote.*.url:git@github.com:company-a/**"]
    path = work.gitconfig
[includeIf "hasconfig:remote.*.url:https://github.com/company-a/**"]
    path = work.gitconfig
```

**Generation rules**

- Paths with `/` and a trailing slash (the trailing slash makes the rule recursive); always `gitdir/i` because NTFS is case-insensitive.
- An organization rule always generates both URL variants, SSH and HTTPS.
- Write order: folder rules first and remote rules after. If several match, the last one wins for each key, so the more specific rule (remote) prevails.
- The app detects conflicts (two profiles with different emails that can match the same repo) and shows them on the rules screen before saving.

**Known limitation.** During a manual `git clone`, remote or folder rules may not apply to the initial download because the repo doesn't exist yet. Smart Clone solves this by passing the configuration with `-c` (section 9); from the first commit on, the rules always apply.

**Default profile (initial value).** The profile marked as "default" is included unconditionally at the top of rules.gitconfig: it applies to every repo without a rule, and any matching rule overrides it. There can only be one. As a configurable alternative, in strict mode a repo with no applicable rule can't commit (`useConfigOnly`).

## 5. SSH management

Each profile pins its key through `core.sshCommand` with `IdentitiesOnly=yes`, so remote URLs stay canonical (`git@github.com:...`) and another profile's key is never offered.

Generated file `~/.gitprofiles/work.gitconfig` (SSH part):

```ini
[core]
    sshCommand = C:/Windows/System32/OpenSSH/ssh.exe -i ~/.ssh/id_ed25519_work -o IdentitiesOnly=yes
```

**Keys**

- Create: `ssh-keygen -t ed25519 -C <email> -f ~/.ssh/id_ed25519_<slug>`. The app never overwrites an existing key.
- Import an existing key, checking that the `.pub` pair exists.
- Copy the public key to the clipboard and open the provider's keys page.
- Check that the private key's ACL only grants access to the user (OpenSSH for Windows rejects the key otherwise) and offer to fix it with `icacls`.

**SSH client** (global app setting)

| Option | Agent | Recommended for |
| --- | --- | --- |
| Windows OpenSSH (`C:/Windows/System32/OpenSSH/ssh.exe`) | Windows `ssh-agent` service | Keys with a passphrase; default |
| SSH bundled with Git for Windows | The Git Bash session's own agent | Environments without Windows OpenSSH |

The app checks that the `ssh-agent` service is running when the first option is chosen.

**Host aliases (optional)**

For tools that don't read the Git configuration and for the connection test, the app generates `~/.ssh/gitprofile.conf` and adds `Include gitprofile.conf` on the first line of `~/.ssh/config`:

```
Host github-work
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_work
    IdentitiesOnly yes
```

The `Include` goes at the top because OpenSSH applies the first value found for each option. Aliases aren't used in remote URLs.

**Connection test.** `ssh -T git@<host> -i <key> -o IdentitiesOnly=yes`. The app extracts the account the provider returns and shows it next to the profile, warning if it isn't the expected one.

## 6. HTTPS management with Git Credential Manager

The app doesn't inject usernames into URLs or write to Windows Credential Manager: it pins the username per host in the profile and lets GCM handle the secret.

HTTPS part of `work.gitconfig`:

```ini
[credential "https://github.com"]
    username = juan-company
```

With `username` set, GCM picks the right account without showing the account picker.

**Adding the credential** (per profile, once)

1. **Provider flow (recommended).** The app runs `git ls-remote` against one of the profile's repos and GCM opens its usual flow (browser OAuth on GitHub and GitLab). The credential is stored by GCM.
2. **Token pasted into the app.** The app runs `git credential approve` and passes it `protocol`, `host`, `username` and `password` through stdin. The token isn't written to disk or logs and is dropped from memory after the call.

**Other operations**

- Check: `git ls-remote` with `GCM_INTERACTIVE=never` and `GIT_TERMINAL_PROMPT=0`; if it fails, the profile is marked as "invalid credential".
- Remove: `git credential reject` with the same host and username.
- Requirements the app verifies: GCM installed (`git credential-manager --version`) and configured as `credential.helper`.

The behavior with several accounts on the same host and each provider's token model are validated separately (section 15).

## 7. Commit signing

Each profile can sign its commits; the recommended option is SSH signing, because it reuses the key infrastructure from section 5.

```ini
[gpg]
    format = ssh
[gpg "ssh"]
    program = C:/Windows/System32/OpenSSH/ssh-keygen.exe
    allowedSignersFile = ~/.gitprofiles/allowed_signers
[user]
    signingkey = ~/.ssh/id_ed25519_work.pub
[commit]
    gpgsign = true
```

- The signing key can be the same as the authentication key or a dedicated one. On GitHub it also has to be uploaded as a *signing key*, which is a separate entry from the authentication one; the app reminds you of this in the wizard.
- `gpg.ssh.program` is set to the `ssh-keygen` of the same SSH client chosen, so it uses the same agent.
- The app generates `allowed_signers` with each profile's email and public key, so `git log --show-signature` verifies locally.
- GPG is supported as an alternative if the user already has it set up: the app only references the key ID and doesn't manage the keyring.

## 8. Repository diagnostics

Replaces "Fix Repo": it explains which identity, key and account Git will use in a repo and which file each value comes from, and only then proposes changes.

**Input.** Drag a folder, pick it in a dialog or select it from the list of repos detected under folders with a rule.

**Effective values view.** For `user.name`, `user.email`, `core.sshCommand`, `credential.*.username`, `gpg.format`, `user.signingkey` and `commit.gpgsign`, the app runs `git config --show-origin --show-scope --get <key>` and shows the value, scope and origin file. The origin file shows which profile was applied.

**Detected problems**

| Problem | How it's detected | Proposed action |
| --- | --- | --- |
| No applicable profile | No key comes from `~/.gitprofiles/` | Create a folder or organization rule |
| Local configuration overriding the profile | `local` scope on `user.*`, `core.sshCommand` or `credential.*` | Remove those local keys |
| Remote with an SSH alias or a username in the URL | Pattern of `remote.*.url` and `remote.*.pushurl` | Normalize to the canonical URL |
| Several profiles match | More than one profile file among the origins | Show the conflict and the winning rule |
| Local commits with someone else's email | `git log @{u}..HEAD --format=%ae` on branches with an upstream | Warning only; rewriting history is out of scope |
| Submodules | `git submodule status` | Recursive diagnostics of each submodule |

Every action first shows the exact change (command or file diff) and is only applied after confirmation.

## 9. Smart Clone

Smart Clone ensures the download uses the profile's credential and that the resulting repo is covered by a rule, without altering the remote URL.

**Inputs**

- URL in any format (`git@host:org/repo.git`, `https://host/org/repo.git`, with or without `.git`). If the clipboard holds a Git URL, it's prefilled.
- Profile, preselected if an organization rule matches the URL.
- SSH or HTTPS method, preselected with `PreferredCloneMethod`. The app converts the URL to the chosen method.
- Destination folder, preselected with the profile's rule folder if there is one.

**Process**

1. Normalize the URL (host, organization, repo) and convert it to the chosen method.
2. Check that, after cloning, a rule will cover the repo (destination folder or URL). If not, offer to create the rule (default option) or, as a flagged alternative, write the identity with `git config --local`.
3. Clone passing the profile's configuration explicitly: `git -c core.sshCommand="..." -c credential.https://<host>.username=<user> clone <url> <destination>`.
4. Run diagnostics (section 8) on the new repo and show the result.
5. Offer to open the folder in Explorer or in SourceTree.

The remote URL stays canonical: no SSH alias or embedded username.

## 10. SourceTree compatibility

SourceTree inherits the profile's identity with no extra steps as long as it uses the system Git and OpenSSH; with its default configuration (embedded Git and PuTTY) the model may fail.

| SourceTree setting | Required value | Reason |
| --- | --- | --- |
| Git version | System Git | The embedded Git may be older than 2.36 and lack `hasconfig` |
| SSH client | OpenSSH | Plink doesn't use `~/.ssh/config` or the Windows `ssh-agent`, and requires keys in PuTTY format |
| "Use global user settings" in each repo | Enabled | If disabled, SourceTree writes `user.*` in the local scope and overrides the profile |

- The app detects SourceTree's configuration read-only and on a best-effort basis, and shows a warning with the steps to fix it. It doesn't modify SourceTree files.
- Diagnostics (section 8) detect the local identity written by SourceTree.
- SourceTree accounts (hosting services) are independent of Git credentials and play no part in push and pull.

## 11. Screens and UX

The app has five views; the global active-profile selector goes away.

| View | Content | Main actions |
| --- | --- | --- |
| Profiles | Side list with a status per profile (SSH key, HTTPS credential, signing: OK / pending / error). Detail in tabs: Identity, SSH, HTTPS, Signing, Rules | Create, edit, duplicate, delete; mark as default; test connection |
| Rules | Table of every rule from every profile, in order of application, with conflicts highlighted | Add, reorder, delete; preview of `rules.gitconfig` |
| Smart Clone | Modal from section 9 | Clone |
| Diagnostics | Effective values and problems from section 8 | Apply fixes with a preview |
| Settings | SSH client, no-profile mode (strict or default profile), detected Git path, backups | Turn the integration on or off; restore a backup |

**First run**

1. Detect Git, its version, GCM and the available SSH client; block with a clear message if Git is older than 2.36.
2. Read the existing global identity and offer to turn it into the default profile.
3. Show the changes that will be made to `~/.gitconfig` and `~/.ssh/config` before turning the integration on.

**Drift warnings.** If a generated file has been edited outside the app (hash different from the recorded one), the app says so and asks for confirmation before regenerating it.

## 12. Stack and technical architecture

C# on .NET 10 (LTS) instead of .NET 8, whose support ends in November 2026.

| Layer | Choice | Notes |
| --- | --- | --- |
| UI | WinUI 3 (Windows App SDK) + CommunityToolkit.Mvvm | No native system tray: adding one requires H.NotifyIcon or Win32 interop |
| Core | .NET library with no UI dependencies | Testable and reusable for a future CLI |
| Git | `git.exe` as a process, with `ProcessStartInfo.ArgumentList` | Not LibGit2Sharp: it doesn't honor `core.sshCommand` or GCM |
| Writing `.gitconfig` | `git config --file <path>` | Git handles escaping and formatting |
| Writing `~/.ssh/config` | Text, only the `Include` line | The rest lives in `gitprofile.conf`, owned by the app |
| Persistence | `profiles.json` in `%APPDATA%` | No SQLite or DPAPI: there are no secrets to protect |
| Packaging | Classic installer (still to be decided versus MSIX) | MSIX redirects writes to `%APPDATA%` into the package folder |

**Core modules**

- `ProfileStore`: loads and saves `profiles.json`.
- `ConfigGenerator`: generates `rules.gitconfig`, `<slug>.gitconfig`, `gitprofile.conf` and `allowed_signers`.
- `GitRunner`: finds Git, checks its version and runs commands.
- `SshManager`: keys, ACL, agent and connection test.
- `CredentialService`: `git credential approve/reject` and checking with `ls-remote`.
- `RepoDiagnostics`: analysis and fixes from section 8.
- `FileGuard`: atomic writes, backups and drift detection (section 13).

**Tests.** Integration tests against a temporary HOME using `GIT_CONFIG_GLOBAL` and `HOME`, so the developer's real configuration is never touched.

**Locating files.** The path of the global `.gitconfig` is obtained from Git (`git config --global --list --show-origin`), not assumed, because `HOME` may be redirected.

## 13. Security, files and rollback

The app stores no secrets and only modifies two user files, in both cases with a single line.

| File | Owner | Operation |
| --- | --- | --- |
| `~/.gitconfig` | User | Adds `[include] path = ~/.gitprofiles/rules.gitconfig`; optionally removes the global `user.name`/`user.email`, saving their values |
| `~/.ssh/config` | User | Adds `Include gitprofile.conf` on the first line |
| `~/.gitprofiles/rules.gitconfig` | App | Regenerated on every save |
| `~/.gitprofiles/<slug>.gitconfig` | App | Regenerated on every save |
| `~/.gitprofiles/allowed_signers` | App | Regenerated on every save |
| `~/.ssh/gitprofile.conf` | App | Regenerated on every save |
| `~/.ssh/id_ed25519_<slug>` | User (created by the app) | Created only; never overwritten or deleted |
| `%APPDATA%\GitProfileManager\profiles.json` | App | Profile metadata and hashes of the generated files |

**Writing rules**

- Atomic writes: temporary file and replace.
- Dated backup in `%APPDATA%\GitProfileManager\backups\` before modifying any user file.
- "Generated by GitProfile Manager" header in the app's own files and a recorded hash to detect external edits.
- A mandatory preview (diff) before changing a user file.

**Secrets.** A token pasted into the app only exists in memory until it's passed through stdin to `git credential approve`; it never appears in process arguments, logs or files.

**Processes.** Arguments are always passed with `ArgumentList`, never concatenated, and URLs are validated before use.

**Turning off and uninstalling.** "Turn off integration" removes the two include lines and restores the saved global identity. Uninstalling does the same and offers to delete the generated files; SSH keys are never deleted.

## 14. Scope

The MVP covers the full lifecycle of an identity: create it, assign it, authenticate with it and check that it's applied.

| Phase | Includes |
| --- | --- |
| MVP | Profiles and file generation · folder and organization rules · SSH keys with `IdentitiesOnly` and connection test · HTTPS via GCM · repo diagnostics · Smart Clone · first run with migration of the global identity · clean turn on and off |
| v1.1 | Commit signing · SourceTree configuration detection · submodule diagnostics · advanced detection of conflicts between rules |
| v1.2 | System tray (Smart Clone from the clipboard, diagnose a folder, drift warnings) · CLI on the same core · import of existing `Host` entries from `~/.ssh/config` |

**Out of scope**

- WSL and Git inside Linux distributions.
- Rewriting history to fix commits already made.
- Managing accounts or keys on the providers through their APIs.
- macOS and Linux.
- Syncing profiles between machines.

## 15. Risks and open questions

Four technical assumptions must be validated with a proof of concept before the design is closed; the rest are product decisions.

**Technical validation**

- [ ] Whether `hasconfig:remote.*.url` and `gitdir` apply during a manual `git clone` or only once the repo exists.
- [ ] Precedence of `core.sshCommand` over the `GIT_SSH` variable SourceTree sets when it uses PuTTY.
- [ ] GCM behavior with several accounts on the same host, per provider (GitHub, GitLab, Bitbucket).
- [ ] Bitbucket's current token model for HTTPS.

**Product decisions**

- [x] No-profile mode: strict (`useConfigOnly`) or default profile as the initial value. Decided: default profile.
- [ ] WinUI 3 or WPF, depending on the priority of the system tray.
- [ ] Classic installer or MSIX.

**Risks**

- Corporate configuration in the `system` scope (for example, a `credential.helper` enforced by GPO) that contradicts the app's. Mitigation: diagnostics show the scope of each value.
- Users with a complex `~/.ssh/config` (`Host *` blocks with `IdentityFile`). Mitigation: `IdentitiesOnly` in `core.sshCommand` doesn't depend on that file.
- Generated files edited by hand. Mitigation: drift detection and confirmation before regenerating.
